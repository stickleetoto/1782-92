# v0.1.5 field-failure mapping

This pass is based on real long-session character-modeling traces rather than synthetic microbenchmarks.

| Field failure | v0.1.5 response |
|---|---|
| Repeated generated helper libraries consumed large model context | Built-in `M.material/mesh/tube/clump/panel/ellipsoid` vocabulary inside `apply` |
| `exec(compiled, env, {})` caused helper/comprehension `NameError` retries | Shared `exec(compiled, env, env)` namespace |
| One giant Python batch could occupy Blender's main thread until the transport timed out | Source/AST budget plus cooperative 15 s Python deadline |
| A request could time out while still queued and execute later | Timed-out queued jobs are marked cancelled before dispatch |
| After an apply stall, subsequent inspect calls piled up or failed | Shorter apply transport window and bounded pending queue |
| `objects`, `quality`, `rings`, and large changed lists flooded model context | Bounded global listings, aggregated quality codes, sampled rings, truncated deltas |
| Expensive successful work could exist several revisions beyond the latest checkpoint | >=2 s successful apply auto-checkpoints; `checkpoint:true` forces one |
| New MCP process could silently talk to an older Blender bridge | Exact v0.1.5 bridge-version check with restart hint |
| Non-object scene edits such as materials/node groups could be reported as no-op | Added non-object mutation signature without counting REF-loaded images |

## Residual limitation

The execution deadline is cooperative Python tracing. It cannot safely interrupt one native Blender C operation that blocks the main thread for a long time. Such a transport failure remains ambiguous; mutating calls must never be replayed blindly.
