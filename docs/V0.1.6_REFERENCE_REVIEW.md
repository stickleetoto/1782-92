# v0.1.6 reference review and overload hardening

1782-92 keeps the public MCP surface at exactly three tools: `inspect`, `apply`, and `render`.

## Patterns adopted from public Blender MCP implementations

- Queue-bypassing health/status probe so the client can tell the difference between an offline bridge and a Blender main-thread job that is merely busy.
- Compact scene comprehension (`tree`, `find:TERM`, `oN:spatial`) instead of repeatedly dumping global object state.
- Current 3D viewport capture for visual feedback in GUI Blender, while retaining deterministic fast/lookdev/wire validation renders.

## Patterns deliberately rejected

- Tool-count explosion into dozens or hundreds of primitive modeling calls.
- Unrestricted Python execution.
- Forced network auto-update.
- External text/image-to-3D services as a dependency of the local control path.

## Field hardening after real Speaky sessions

Real GPT/Codex sessions also showed a second failure class: once one generated operation exceeded what Blender or the MCP transport could comfortably sustain, stale requests and large payloads could make the bridge itself appear dead. v0.1.6 therefore adds defense in depth:

- Single-flight admission: at most one non-status Blender job can be queued/running. Extra requests fail fast with `bridge_busy` instead of building a stale queue.
- Ambiguous mutation circuit breaker: if an `apply` transport times out while already running, the bridge reports `recover=1` and refuses another `apply` until a successful read-only inspect observes the actual post-timeout scene.
- `status` continues to bypass Blender's main-thread queue and now reports active job id/age, recovery state, and last job timing/result.
- Literal `range(...)` loops above the configured bound and statically obvious `bpy.ops` workloads above the safe budget are rejected before Blender execution. This complements the cooperative Python deadline, which cannot pre-empt one long-running C call inside Blender.
- Risky or explicitly checkpointed applies create a pre-mutation recovery copy before execution; failures can return the known-good checkpoint.
- Route-specific request limits and an encoded image response budget prevent oversized JSON/image payloads from overwhelming the local HTTP/MCP path.
- Reference previews have a total raw-byte budget and viewport capture is capped before base64 encoding.
- Viewport/reference renders use shorter MCP timeouts than full scene validation renders.

## Runtime gates

Before merge:

1. GitHub CI must pass.
2. Blender 5.2.1 headless smoke must pass cleanly.
3. GUI `inspect("status")`, `tree`, `find`, `spatial`, and `render({mode:"viewport"})` must pass.
4. Run one overload/recovery check: submit a policy-blocked large operator loop and confirm it is rejected without changing scene revision; then run a small normal apply and confirm the bridge remains responsive.

The goal is not to make Blender itself uncrashable. Operations inside Blender C code cannot be safely pre-empted from an in-process add-on. The goal is to reject obvious overload before execution, prevent queue avalanches, preserve a recovery point, expose clear busy/recovery state, and keep the MCP process responsive enough to recover deterministically.
